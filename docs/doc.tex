\section{The goal}

This project builds our own "serverless" (FaaS - Function as a Service) platform,
inspired by ones like AWS Lambda. The goal is create a system, which can based
on incoming HTTP requests dynamically start instances, process the request and
then teardown the instance. Thus removing the need of a permanently running server.

\section{Architecture}

Architecture is split into multiple components:

\begin{enumerate}
	\item \textbf{API Gateway:} Service, which accepts incoming requests,
	      transforms them into a inner system representation and sends
	      them further into the system.
	\item \textbf{Commander:} The "brain" of the whole system. Decides which
	      instance to use for incoming requests, whether to create new one (cold start),
	      or reuse already running one (warm). Also responsible for storing
	      user function binaries and serves them to the rest of the system.
	\item \textbf{Runner:} Component running on execution nodes, which process
	      the incoming requests by executing user's functions.
	\item \textbf{Guest:} The user's submitted functions. They take in
	      the request, process it, and return a response.
\end{enumerate}

\section{Tech stack}

The platform is built with the following technologies:

\begin{itemize}[leftmargin=*]
	\item \textbf{Golang}: used as the programming language \href{https://go.dev/}{go.dev}.
	\item \textbf{HTTP}: used for public ingress.
	      \begin{itemize}[leftmargin=*]
		      \item The Gateway accepts client requests over HTTP.
		      \item The Commander function binaries API is also HTTP-based. It is defined with \href{https://www.openapis.org/}{OpenAPI} and generated with \href{https://github.com/oapi-codegen/oapi-codegen}{oapi-codegen}.
	      \end{itemize}
	\item \textbf{gRPC}: used for inner system communication \href{https://grpc.io/}{grpc.io}.
	\item \textbf{SQLite}: used by Commander for storing data \href{https://sqlite.org/}{sqlite.org}. We chose it because we did not need to complicate the stack more and SQLite is enough for now; because the SQLite implementation is behind an interface, we could swap it for PostgreSQL easily.
	      \begin{itemize}[leftmargin=*]
		      \item Query code is generated with \href{https://sqlc.dev/}{sqlc} to keep database access type-safe.
	      \end{itemize}
	\item \textbf{Structured logging}: implemented with Go's \href{https://go.dev/blog/slog}{slog}.
	\item \textbf{Instrumentation}: based on \href{https://opentelemetry.io/docs/languages/go/}{OTEL}.
	      \begin{itemize}[leftmargin=*]
		      \item HTTP server instrumentation uses \href{https://github.com/riandyrn/otelchi}{otelchi}.
		      \item gRPC instrumentation uses \href{https://pkg.go.dev/go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc}{otelgrpc}.
	      \end{itemize}
	\item \textbf{Visualization}: provided by the \href{https://grafana.com/}{Grafana} stack.
\end{itemize}

\section{API Gateway}

The API Gateway is the stateless public HTTP entrypoint of the system. It receives
requests from clients, extracts the function identifier from the URL,
normalizes the request into the internal format used by the platform, and then
asks the Commander where the request should be executed. After Commander
returns the selected runner and instance identifier, the Gateway forwards the
invocation to that runner and sends the response back to the client.

\section{Commander}

The Commander is the control plane of the platform. It keeps track of the
current system state and decides where each request should be executed.
Conceptually, it acts as the brain of the system: it knows which runners are
available, which function instances are already running, and whether a request
should reuse an existing warm instance or trigger a cold start.

To maintain this knowledge, the Commander periodically polls runners for
heartbeats. Those heartbeats report runner availability, queue depths, and
resource usage, so the Commander can avoid overloaded or unavailable runners
when making routing decisions.

The Commander also exposes an HTTP API for uploading and downloading function
binaries. Uploaded functions are stored and later served to runners when a new
instance needs to be started and the runner doesn't have the function copy locally.

For request routing, the Commander exposes a gRPC API used by the Gateway. The
Gateway calls this API for each incoming request to ask for the routing
decision, and the Commander returns the selected runner address together with
the instance identifier that should handle the invocation. Figure~\ref{fig:commander-routing}
shows the routing flow.

\section{Runner}

The Runner is the most complex part of the platform. It has to coordinate
parallel instance startup, shutdown, binary downloads, and request execution at
the same time, while still merging concurrent requests for the same function
into one starting instance instead of spawning duplicate processes.

The coordination model is the main challenge. The runner keeps track of
instances that are already running, instances that are still starting, and
downloads that are already in flight. When several requests arrive at once,
they all wait on the same startup or download result, which lets them collapse
into one shared preparation path. Once an instance is running, requests are
serialized through its queue, and idle instances are stopped after the
configured timeout.

The runner launches each function inside a runtime and communicates with it
through the guest's gRPC server. Right now only the native runtime is
implemented, where the binary is started directly on the host, a free port is
assigned, and the guest is expected to serve gRPC on that port. The
abstraction is intentionally small, so adding another runtime would not be
difficult: a Docker runtime could copy the binary into a container and expose
the gRPC port, while a JavaScript runtime could do the same with raw JS source
and a container that provides a JS engine.

\section{Guest}

Guests are the user functions themselves. At the moment we provide only a Go
SDK, which wraps the function and starts the gRPC server expected by the
runtime. For other languages, SDKs for them would be similar, because gRPC implementations
exists for many languages.

The only requirement from the runtime is that it provides the environment
variables needed to configure the guest server, such as the address it should
bind to.
